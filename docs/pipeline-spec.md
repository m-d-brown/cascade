# Pipeline Specification

This document details the YAML configuration format used by `cascade run`, `cascade check`, and the `interpreter` package.

A pipeline file (typically `cascade.yaml` or any file passed to `-f`) declares a directed graph of shell actions, their execution dependencies, and freshness rules for caching.

---

## File Structure

```yaml
name: build # optional, defaults to the file's basename without extension

actions:
  checkout:
    run: git fetch && git reset --hard origin/main

  deps:
    run: go mod download
    needs: [checkout]

  compile:
    run: go build -o build/app ./cmd/app
    needs: [deps]
    produces: [build/app]
    sources: ["**/*.go"]

  snapshot:
    run: restic backup ~
    every: 24h

  release: # Barrier: no run command; waits for dependencies to finish
    needs: [compile, snapshot]
```

### Top-Level Fields

| Field     | Type   | Description                                                                       |
| :-------- | :----- | :-------------------------------------------------------------------------------- |
| `name`    | string | Optional identifier for the pipeline. Defaults to the base name of the YAML file. |
| `actions` | map    | Map of action names to action definitions. The action name is the map key.        |

---

## Action Fields

Every action is configured under its unique key in `actions`. All fields within an action are optional.

### Execution

- **`run`** (`string`): The shell command to execute. Executed via `sh -c`, so environment variables, pipes, and compound commands (`&&`, `||`, `;`) work as written. If omitted, the action acts as a **barrier**: it waits for all actions listed in `needs` to finish before completing.
- **`dir`** (`string`): Working directory for `run` and `unless`. Relative paths in `produces` and `sources` are also resolved relative to `dir`. A leading `~` is expanded to the user's home directory.
- **`env`** (`map[string]string`): Additional environment variables supplied to `run` and `unless`. These variables augment the ambient process environment rather than replacing it.
- **`timeout`** (`string`): Maximum allowed duration for `run` and any associated freshness checks, formatted as a Go duration string (e.g., `30s`, `5m`, `1h`). If the command exceeds this limit, it is killed and the action fails.
- **`allow-exit`** (`[]int`): Non-zero process exit codes treated as warnings rather than failures.
- **`optional`** (`bool`): When `true`, if the command fails, the action status is recorded as `Skipped` instead of `Failed`. Subsequent actions that depend on this action will still execute.

### Dependencies

- **`needs`** (`[]string` or `string`): List of prerequisite actions that must complete successfully before this action starts. In YAML, a single string can be provided instead of a list. If any required dependency fails or is skipped due to an upstream failure, this action is blocked and marked as `Skipped`.

### Documentation & UI

- **`description`** (`string`): A single-line description of the action, displayed in summary tables, `cascade dot`, and status views.
- **`progress`** (`string`): A companion shell command polled while `run` executes. The latest line emitted by `progress` becomes the action's status line in the live terminal tree. If omitted, Cascade uses the latest output line from `run` itself.
- **`progress-every`** (`string`): Polling interval for progress reporting, formatted as a Go duration string. Defaults to `15s` when `progress` is specified, and `2s` when tracking `run` directly.

## Freshness and Caching

Cascade determines whether an action needs to run using three freshness mechanisms: file timestamps, run intervals, and custom shell checks.

If an action configures multiple freshness checks, **all active checks must agree that the action is fresh**. If any check reports stale, the action runs.

### 1. File Timestamps (`produces` and `sources`)

- **`produces`** (`[]string` or `string`): Output file paths generated by the action. Must be literal file paths (globbing is not supported in `produces`).
- **`sources`** (`[]string` or `string`): Input file paths or glob patterns. Supports standard glob syntax as well as recursive directory wildcards (`**`).

**Evaluation rule:** The action is considered fresh only if **every** file listed in `produces` exists and has a modification timestamp newer than **every** file matched by `sources`. If any output is missing, or if any source file is newer than any output file, the action is considered stale and runs.

### 2. Time Intervals (`every`)

- **`every`** (`string`): Minimum duration between successful runs (e.g., `24h`, `30m`).

**Evaluation rule:** Cascade consults the execution journal. If the action succeeded under an identical configuration fingerprint within the specified duration, the action is considered fresh and is skipped.

### 3. Shell Exit Checks (`unless`)

- **`unless`** (`string`): A shell command executed before `run`.

**Evaluation rule:** If the command exits with status code `0`, the action is considered already complete and is skipped. If it exits with a non-zero status code, the action is considered stale and proceeds to run.

### Cascading Staleness

When an action executes, any downstream action whose `sources` overlap with the upstream action's `produces` is automatically recognized as stale and will also run. Changes near the top of the dependency tree propagate down through dependent nodes.

### Dry-Run Behavior

When running under dry-run mode (`cascade run --dry-run` or `cascade plan`), all freshness checks report stale. This guarantees that `cascade plan` shows the full intended execution path regardless of the current filesystem state.

## Preflight Validation (`cascade check`)

`cascade check` parses and inspects the pipeline configuration before executing any commands.

### Errors (Prevent Execution)

- Syntax or YAML formatting errors.
- Cycles in the `needs` graph.
- References to non-existent action names in `needs` (dangling dependencies).
- Actions defined more than once.
- Unknown configuration fields.
- Invalid duration strings for `every`, `timeout`, or `progress-every`.

### Warnings (Reported but Execution Allowed)

- Barriers (actions with no `run`) that configure freshness fields (`produces`, `sources`, `every`, `unless`) or execution controls (`env`, `dir`, `timeout`, `allow-exit`).
- Actions with `sources` but no `produces` (file modifications cannot be detected).
- Multiple actions declaring the same file path in `produces`.
- Redundant dependency entries in `needs`.
